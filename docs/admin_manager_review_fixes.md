## Restore operation and recovery

All web workers must use the same checkout and lock directory on the same host.
The filesystem guard does not stop another host, shell command, scheduled job,
database event or direct MySQL client. Stop these writers and concurrent DDL
before acknowledging the maintenance window, and leave them stopped until the
result has been validated. Do not remove or replace `.maintenance.lock` while
workers run. The backup directory must be writable by the application account
and protected from uploads or untrusted filesystem writes. The audit file uses
append logging; rotate/archive it while workers are stopped, avoiding competing
Windows file rollover by multiple processes.

Verification checks trusted mysqldump structure, completion, size and persisted
SHA-256. It detects incomplete or changed files; it does not prove arbitrary SQL
is safe, nor does each HTTP request perform a disposable restore rehearsal.
Only system-created files and manifests in the protected backup directory are
accepted. Full replay of generated backups is tested separately on disposable
MySQL databases.

If restore fails, keep external writers stopped. Read the retained snapshot name
and destination from `database/backups/.restore-recovery.json` and the audit log.
Keep both its `.sql` and `.sql.json` files. An operator must verify the snapshot,
rehearse it on a new disposable database and restore the confirmed destination
under maintenance using the configured MySQL client and SQL stdin. Validate
migration history, authentication, products and CRM data before removing the
recovery marker and resuming access. The web restore endpoint stays blocked
while that marker exists. MySQL DDL/import can apply partially; no automatic
rollback is promised. Do not delete the marker merely to make the application
reachable.
